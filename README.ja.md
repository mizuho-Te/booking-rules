# booking-rules

予約を保存する前に、資源ごとの重複・準備時間・利用不可期間・延長を確認する、小さな Python ライブラリと UTF-8 JSON CLI です。

[English](README.md) · [API仕様](docs/API.md) · [ライセンス状況](LICENSE)

## 現在の状態

バージョン 0.1.0。MIT ライセンスで公開しています。サンプルはすべて架空のデータで、導入実績・利用者数・業務上の成果を主張しません。Python 3.11 以上、実行時の外部依存なし。Linux・Windows・macOS × Python 3.11〜3.13 のCI設定を用意していますが、設定を置いたことと実際にリモートで通過したことは別です。

## 何に使える？

会議室や機材を借りるアプリで、「10時〜11時に予約できるか」「前後の準備時間を含めても空いているか」「既存予約を延長できるか」を判定します。

判定には理由コードと衝突相手のIDが含まれます。通常の時間重複・準備時間だけの重複・利用不可期間を区別でき、別の資源には影響しません。入力データを書き換えず、入力順序が違っても同じ結果になります。

## すぐ試す

リポジトリのフォルダで実行します。インストールは不要です。

```sh
python examples/run_demo.py
python -m unittest discover -s tests -v
```

デモは実際のCLIに架空の日本語IDを渡し、「準備時間が重なる」結果を表示します。Windowsでもシェルのリダイレクト構文に依存しません。リダイレクト対応シェルの場合は次でも実行できます。

```sh
python -m booking_rules < examples/buffer-conflict.json
```

CLIの終了コードは、許可 `0`、衝突あり `1`、入力不正 `2`。衝突ありは処理失敗ではなく正常な判定結果です。標準入力へUTF-8のJSONを1件渡し、入力を閉じてください。結果は標準出力にJSONで返ります。

## Pythonから呼ぶ

```python
from booking_rules import evaluate

result = evaluate({
    "operation": "check",
    "bookings": [],
    "candidate": {
        "id": "新規予約", "resource_id": "会議室A",
        "start": "2026-10-21T10:00:00+09:00",
        "end": "2026-10-21T11:00:00+09:00",
        "buffer_before_minutes": 15,
        "buffer_after_minutes": 10
    }
})
print(result["allowed"])
```

入力不正は `ValidationError` です。別のプロジェクトから利用する場合は `python -m pip install .` でローカルインストールできます。ビルド時のみ setuptools が必要です。

## 大事なルール

- 日時には秒と時差を明記します。`+09:00` または `Z` などを指定し、時差不明の日時・日付だけ・タイムゾーン名・うるう秒は受け付けません。
- 区間は `[開始, 終了)`。前の有効区間の終了と次の有効区間の開始が同時刻なら重複しません。
- 前後の準備時間は予約の占有区間を広げます。前の予約と次の予約の両方の準備時間が数えられます。
- 利用不可期間は準備時間を含む候補全体をブロックします。
- 延長では既存予約の終了だけを後ろへ動かし、その予約だけを比較対象から除きます。開始・資源・ID・準備時間は変更できません。追加部分だけでなく延長後の全区間を再確認します。
- 全既存予約どうしを総当たり監査する機能ではなく、候補1件の判定です。ただし他資源も含め全入力を検証します。

## できないこと・安全な組み込み方

`allowed: true` は渡されたデータの時点で空いている、という意味です。予約の確定・保存・同時操作の排他制御はしません。2人が同時に空きを確認した場合、両方が許可になる可能性があります。アプリ側で権限確認と、判定から保存までのトランザクション・ロック・DB制約を実装してください。

通信・DB・料金・顧客情報・定期予約・タイムゾーン推測は扱いません。資源ごとの定員は1件分を想定します。個人情報はIDやログへ入れないでください。
